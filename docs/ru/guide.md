# Установка, управление и разработка

[English](../en/guide.md) | [README](../../README.ru.md)

## Установка и сеть

Во время работы облако не требуется. До отключения WAN заранее получите бинарники, Docker-образ и конфигурацию. Не открывайте порты устройства и API в интернет. Ограничивайте DNS/NAT целевым устройством и сохраняйте отдельный доступ к роутеру для отката.

### Windows

Соберите два исполняемых файла и сохраните рядом `windows/`:

```sh
GOOS=windows GOARCH=amd64 go build -o out/windows/autoblow-server.exe ./cmd/autoblow-server
GOOS=windows GOARCH=amd64 go build -ldflags="-H windowsgui" -o out/windows/AutoblowLocal.exe ./cmd/autoblow-windows
```

Скопируйте `windows/` и `docs/` в `out/windows/`; откройте `AutoblowLocal.exe`. Оболочка использует Windows PowerShell 5.1, .NET Framework и WinRT. Python, WSL и Docker Desktop пользователю не нужны. Выберите автономную точку доступа либо работу через роутер. Для точки доступа нужен адаптер с Wi-Fi Direct; начальная настройка и DHCP/DNS требуют физической приёмки. Подключите устройство к показанной Wi-Fi-сети штатным способом. Для возврата в прежнюю сеть потребуется снова выполнить штатную настройку.

Данные и пароль точки доступа находятся в `%LOCALAPPDATA%/AutoblowLocal`. Не публикуйте этот каталог. Необязательный `control-options.json` использует поля сервера `compatibilityControl`, `experimentalSyncScripts`, `experimentalLocalScripts`, `maxSpeed`, `scriptURLOrigins`. Правьте его при остановленном приложении. При штатной остановке сначала проверяется и завершается собственный сервер, затем точка доступа. Если завершение процесса не подтверждено, оболочка сохраняет соединение и оставляет STOP для восстановления.

### Docker на NAS

Соберите Linux-сервер в отдельном контексте с `deploy/Dockerfile` и `/etc/ssl/certs/ca-certificates.crt`, затем образ `autoblow-local:0.2.0-rc.2`. В scratch-образе находятся исполняемый файл и доверенные CA. Сохраните его через `docker save` и перенесите архив для автономного `docker load`.

Задайте `AUTOBLOW_DATA_DIR` и `AUTOBLOW_CONFIG_DIR` как приватные абсолютные пути. Скопируйте во второй каталог `deploy/server.example.json` с именем `server.json`. UID/GID 65532 нужны запись в данные и чтение конфигурации. `deploy/compose.yaml` задаёт `pull_policy: never`, `restart: no`, read-only корень, 96 MiB и отсутствие дополнительных capabilities. Порт TLS хоста 20445 соответствует 20443 контейнера, API 20881 - 20880. Публикация репозитория ничего не устанавливает и не запускает на NAS.

### Варианты DNS и роутера

Адреса в примерах условные: роутер `192.168.50.1`, сервер `192.168.50.10`, устройство `192.168.50.60`.

1. **DNS через DHCP только устройству.** В OpenWrt/dnsmasq назначьте устройству tag и DHCP option 6 с отдельным DNS. Настройте локальную wildcard-зону `autoblowapi.com`. Устройству нужен TCP 443 сервера. Ограничьте настройку его MAC/резервацией.
2. **Записи роутера, Pi-hole или AdGuard.** Перенаправьте `latency.autoblowapi.com` и выбранный региональный узел, например `eu-central-1.autoblowapi.com`. Лучше использовать поддерживаемую локальную wildcard-зону; не оставляйте конкурирующий публичный AAAA-ответ. Общие записи действуют на всех клиентов этого DNS, включая другие устройства Autoblow.
3. **NAS с занятым 443.** В DNS только устройства верните LAN-адрес роутера. Ограниченный источником устройства DNAT направляет TCP 443 на 20445 сервера, UDP/TCP 53 на порт локального DNS. Нужен соответствующий hairpin SNAT, чтобы ответ вернулся через роутер. DNS не выбирает порт; трафик в той же подсети, отправленный сразу на NAS, обходит DNAT роутера.

Схемы применимы к OpenWrt и MikroTik с их синтаксисом DHCP/firewall; проверяйте реальные совпадения правил и счётчики. Для отката остановите управление, верните только изменённые DHCP/DNS/NAT-записи и переподключите устройство. Не очищайте глобальные conntrack или DNS. Проверяйте отсутствие WAN в отдельной сети либо запретом только устройству. Физическая приёмка этих путей с Go-сервером пока открыта.

## API и протокол

Устройство использует `wss://latency.autoblowapi.com/device-backend/ws`, TCP 443. Заголовки сообщают hardware `vacuglide`, firmware `1.03`/`1.0.3`, MAC и токен устройства. Сервер сравнивает токен с SHA-256 только в памяти. Для панели создаётся отдельный ключ `dataDir/control-token`.

Для всех `/api/*` нужен `Authorization: Bearer <локальный-ключ>`. `/health` и статические файлы доступны без раскрытия учётных данных. Сопряжение - `POST /api/pair`, для симулятора `{"mac":"020000000001"}`. Из `/api/status` возьмите текущую `generation`; `/api/start` принимает `{"speed":15,"seconds":60,"generation":1}` и возвращает `controlEpoch`. Продлевайте его через `/api/keepalive` каждые 400 мс. Действуют двухсекундный lease и исходная длительность. `/api/stop` отменяет ожидающие операции и проверяет ответы о паузе мотора и закрытии клапанов.

Совместимые `/vacuglide/*` и `/autoblow/*` используют `x-device-token`, принимают локальный ключ и требуют сопряжения и `compatibilityControl` для записи. Остановкой здесь управляет внешний клиент, таймер панели не применяется. Для сценариев включаются `experimentalSyncScripts` и/или `experimentalLocalScripts`; воспроизведение требует `maxSpeed: 100`, поскольку штатные сценарии могут содержать полный диапазон скорости. Для импорта по URL нужен явный список `scriptURLOrigins`; пустой список запрещает загрузки наружу.

[Машиночитаемый контракт](../contracts/vacuglide2-control-api.json) перечисляет маршруты и отличия локальной политики. Ответы проверяются и связываются по UUID; успех без ответа устройства не выдумывается. Виртуальный клиент намеренно генерирует синтетические ответы.

```text
/target-speed-set/15/<uuid>
/target-speed-stop/<uuid>
/valve-stroke-plus-set/1/<uuid>
/valve-stroke-minus-set/0/<uuid>
/state/<mode>/<slot>/<speed>/<plus>/<minus>/<time>/<offset>/<loop>/<token>/<uuid>
```

43/44 - ручное воспроизведение/пауза, 41/42 - локальный сценарий, 60/70 - sync-сценарий. STOP может сохранять последнюю заданную скорость. Ненулевая скорость не доказывает движение. Штатная пауза сценария может сохранять состояние клапанов; STOP панели закрывает их отдельно. `stopConfirmed` означает подтверждение прошивки, а не физического датчика.

Бинарный файл содержит восьмибайтовый little-endian заголовок: ID сценария и маркер формата 1. Затем шестибайтовые записи: `uint32 миллисекунды`, `uint8 opcode`, `uint8 value`. Opcode 0 задаёт скорость, 1 - stroke-minus, 2 - stroke-plus. Сохраняйте порядок, одинаковые времена и неизвестные операции. Из скоростного результата нельзя восстановить исходное направление или события клапанов. Для временной семантики есть отдельная автономная tick-модель.

## Инструменты разработки

- `cmd/vacuglide-simulator`: WSS-клиент только для loopback, с проверкой TLS, синтетическим MAC и ограничением загрузок. `--lab --duration 10m` создаёт отдельный стенд. Для своего локального сервера: `--url wss://127.0.0.1:20443/device-backend/ws --ca local-server.crt`. Режима отключения TLS, внешнего сервера и реальных учётных данных не требуется.
- `internal/simulator`: модель ручных команд, клапанов, local/sync и слотов. Она сообщает запрошенное состояние, не воспроизводит сценарий по реальному времени, мотор, flash или OTA. `research/vacuglide_tick_model.py` отдельно моделирует время автономно.
- `research/vacuglide_binary.py`: декодирование/кодирование без потерь и кандидат преобразования Funscript. Пример: `python research/vacuglide_binary.py decode input.bin output.json --csv analysis.csv`. Выходные файлы не должны существовать.
- `research/inspect_esp_image.py` и `research/ghidra/`: ограниченный статический анализ образа и экспорт из Ghidra. Образ предоставляет оператор; прошивка не записывается и не входит в репозиторий.
- `research/virtual-cloud-probe.mjs`: сохранённый эксперимент облачного протокола с явным включением. По умолчанию dry-run. Запуск требует приватных файлов, нового явного решения оператора и `VACUGLIDE_PROBE_POWER_OFF=CONFIRMED` после физического отключения собственного устройства. Не используйте его вместо локального симулятора, не запускайте в CI и не добавляйте входные/выходные данные в Git.
- `reference/vg_protocol.py`: исходный минимальный Python-кодек для сравнения протокола.

### Проверки

```sh
go test -race ./...
go vet ./...
python -m unittest discover -s research -p 'test_vacuglide_binary.py' -v
python -m unittest discover -s research -p 'test_vacuglide_tick_model.py' -v
python scripts/test_package_release.py -v
node scripts/panel-contracts.mjs
python scripts/prepare-client-contracts.py
npm ci --prefix out/clients-integration --ignore-scripts --no-audit --no-fund
AUTOBLOW_TEST_NODE=$(command -v node) AUTOBLOW_TEST_CLIENTS="$PWD/out/clients-integration" go test -race -tags integration ./core
```

Node 24.18.0 поддерживает TypeScript-адаптер стенда; SDK 2.6.0 зафиксирован lock-файлом. Снимок адаптера - тестовая фикстура совместимости; установленная Studio проверяется отдельно. Для получения зависимостей нужен интернет либо заполненный кеш, сами тесты и готовый сервер работают автономно.

Перед коммитом запускайте `node .standards/check.mjs staged`. Владелец использует отдельный build-хост для тяжёлых операций; публичные PR нельзя автоматически исполнять на приватном runner. GitHub-задача `repository-standard` проверяет инструменты с правами только чтения. Статус `software-verification` относится к точному исходнику, проверенному на изолированном build-хосте; физическая приёмка учитывается отдельно.
